# Block Plan Model & Distinction Framework — SIH26027

This document defines the structure of a **Block Plan** and clarifies the critical distinction between **Requested Work**, **Candidate Opportunities**, and **Recommended Block Plans**.

---

## 1. Three Fundamental Concepts

To build an explainable, constraint-aware decision-support system, we must never confuse the following three operational concepts:

```
┌───────────────────────────┐
│     1. REQUESTED WORK     │  What departments WANT to do
│    (Raw Work Orders)      │  (Independent, uncoordinated demand list)
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ 2. CANDIDATE OPPORTUNITY  │  Where track access CAN physically happen
│   (Traffic Gap Windows)   │  (Low-density time slots in train timetables)
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│   3. RECOMMENDED PLAN     │  What the engine SELECTS & BUNDLES
│   (Conflict-Free Plan)    │  (Feasible, optimized, explainable schedule)
└───────────────────────────┘
```

### Concept 1: Requested Work
- **Definition:** The raw set of uncoordinated maintenance task requests submitted by Civil, S&T, and TRD departments.
- **Characteristics:** Unconstrained, independently generated, frequently overlapping in space/time, and often exceeding available corridor access capacity.

### Concept 2: Candidate Opportunity
- **Definition:** An identified time-space window on a corridor where train traffic density is low enough to permit line access without violating safety headways.
- **Characteristics:** Derived by analyzing train timetables and freight forecasts. A candidate opportunity is an *unassigned container* awaiting task allocation.

### Concept 3: Recommended Block Plan
- **Definition:** The final output generated by the optimization engine that selects specific requested tasks, bundles compatible cross-departmental work into integrated block windows, assigns scarce resources, and resolves traffic conflicts.
- **Characteristics:** Fully feasible, conflict-free, constraint-validated, and accompanied by human-readable decision rationale and trade-off alternatives.

## 3. Plan Lifecycle States

```
[ PROPOSED ] ──► (Planner Review) ──► [ APPROVED ] ──► (Execution Start) ──► [ IN_EXECUTION ]
      │                                     │                                       │
      ▼                                     ▼                                       ▼
[ REJECTED ]                         [ CANCELLED ]                          [ COMPLETED ]
                                                                                    │
                                                                       (Disruption / Overrun)
                                                                                    │
                                                                                    ▼
                                                                            [ REPLANNED ]
```

- **`PROPOSED`**: Newly generated by the optimization engine; awaiting planner review.
- **`APPROVED`**: Formally signed off by the Railway Maintenance Planner for execution.
- **`IN_EXECUTION`**: Active block window currently underway on the track corridor.
- **`COMPLETED`**: Block window closed, track restored, and execution record filed.
- **`REPLANNED`**: Original plan superseded by dynamic replanning following a live disruption.
